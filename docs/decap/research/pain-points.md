# Chip debugging pain points: what tools exist, and what is still unsolved

*A short guide for a team lead who is new to chips.*

## 1. The picture

Chips are written as code (**RTL**, usually Verilog or SystemVerilog) and tested in a **simulator** (a program that runs the hardware design) against a **testbench** (the test suite). When a test fails, the main evidence is a **waveform dump**. This is a recording of every signal at every clock tick, like a log of every variable at every line of a program. Debugging means reading that log backwards from the failure to the line of RTL that caused it. It is the largest single share of the job, about [47% of verification time](https://semiwiki.com/eda/327016-siemens-eda-on-managing-verification-complexity/). Only [5% of IC/ASIC projects got working first silicon in 2026](https://blogs.sw.siemens.com/verificationhorizons/2026/09/08/the-2026-functional-verification-study/), down from 14.4% in 2024. Companies pay for expensive seats of tools that help. Students and small teams on free tools (Icarus, Verilator, cocotb, GTKWave, Surfer) mostly do this by hand.

**Terms used below:**
- **X**: an unknown value, like reading uninitialised memory.
- **Assertion / SVA**: an `assert` statement written in hardware's language.
- **Formal**: a tool that proves a property exhaustively instead of testing it. When the property fails, it gives a **counterexample**, a short failing trace.
- **Regression**: the nightly CI run.
- **CDC**: signals crossing between clock domains. It behaves like threads sharing data without locks.
- **UPF / SDC**: side files describing power domains and timing rules.
- **Coverage**: which parts of the design the tests actually exercised.
- **MCP**: the protocol that lets AI agents call tools.
- **WCP**: Surfer's remote-control protocol. Other programs use it to drive the viewer.

## 3. Deep dive: waveform debugging

**How it's done today:**
1. A CI test fails ("scoreboard mismatch at 41,230 ns"). Regressions usually run without dumps because the files are huge, so you rerun with dumping turned on.
2. You open the dump at the failure and find the bad signal.
3. You switch to the editor to find which line assigns that signal (its "driver"), decide which of its inputs looks wrong, add those signals, and step back in time.
4. You repeat this across hundreds of cycles and several modules. The bug is ["rarely in the place you are looking"](https://zipcpu.com/zipcpu/2022/08/30/not-my-fault.html).

One vendor case: [a senior engineer estimated 4 hours for one failure and a new engineer about 3 days](https://www.tessolve.com/wp-content/uploads/2025/11/Jeffrey-Pan-1.pdf). The software equivalent is debugging a crash from a full memory trace with no stack trace and no "step back".

**What the viewers do and don't do:**
- **[Verdi](https://www.synopsys.com/verification/debug/verdi.html)** (Synopsys, paid): double-click a value to jump to its source line, one-click driver lookup, X-source tracing, and multi-cycle Auto Trace. A human still picks which input is "wrong" at each step.
- **SimVision/Verisium** (Cadence, paid): ["goto cause"](https://community.cadence.com/cadence_technology_forums/f/functional-verification/14117/tracing-x) steps back through causes. WaveMiner ranks suspect signals, but only if a passing run of the same test and seed exists.
- **Visualizer** (Siemens, paid): advertises fan-in and "time cone" tracing. The product page returned 404, so this is unverified.
- **GTKWave** (free): shows values, not causes. Its search is clunky and [misses partly-X values](https://github.com/gtkwave/gtkwave/issues/471).
- **Surfer** (free): fast, runs in the browser, has a remote mode, and can be driven by other programs over WCP. It computes no drivers itself, and value search is still [unmerged](https://gitlab.com/surfer-project/surfer/-/merge_requests/1008).
- **Free add-ons that close part of the gap:** [ossschem](https://github.com/markusdd/ossschem) and [slang-server](https://github.com/hudson-trading/slang-server) (static driver tracing linked to Vaporview/Surfer), and Vivado's free [`report_drivers`](https://docs.amd.com/r/en-US/ug900-vivado-logic-simulation/Using-the-report_drivers-Tcl-Command). All of these go one hop at a time, by hand.

**What AI tools claim:**
- **Vendor agents:**
  - [Verdi Assistant and a Verdi MCP server](https://semiengineering.com/faster-verification-debug-with-ai/): no benchmarks published.
  - Verisium: customers report 89-97% less debug time (vendor-presented).
  - [Questa One debug agent](https://www.automation.com/article/siemens-integrated-circuit-design-verification-agentic-ai-questa-one): early access, and an engineer approves each step.
  - [AMIQ DVT](https://eda.amiq.com/press-releases/amiq-eda-integrates-code-development-and-debug-with-ai-assistance): evidence-linked reports, no accuracy figures.
- **Startups** (enterprise-only, all self-reported): ChipAgents (56.3% top-1), Bronco (70% in about 15 minutes), [Silogy](https://silogy.io) (">90%" with no data).
- **Free tools:**
  - [Tencent wave-mcp](https://github.com/Tencent/wave-mcp) (Apache-2.0, July 2026): waveform search, driver and X tracing over a SystemVerilog netlist, pass/fail diff, and a Surfer view. The viewer is Linux-only.
  - [TraceWeave](https://github.com/gokeshenzhen/TraceWeave): its own README says results are "leads… not proof".
- **Research:**
  - [FVDebug](https://arxiv.org/abs/2510.15906): formal counterexamples only, no code released.
  - [BTTF](https://arxiv.org/abs/2610.06790): 95% on 150 natural-language queries, no code released.
  - [VCDiag](https://arxiv.org/html/2506.03590v4): finds the buggy module, not the line.
  - [WaveformQA](https://arxiv.org/abs/2607.20638): frontier LLMs get worse on multi-step timing questions.

**What is genuinely unsolved:**
1. A free, *measured* automatic walk from a wrong value back to the guilty line, with a principled stopping rule such as "stop at the first divergence from a passing run". wave-mcp has some of the pieces, but no one has published how often such walks land on the right line.
2. A public benchmark of real failures with waveforms and line-level labels. The ingredients exist ([hardware-bugbase](https://github.com/efeslab/hardware-bugbase), [RTL-Repair](https://github.com/ekiwi/rtl-repair)), but no one has assembled them.
3. A human-facing query bar inside a free viewer.
4. Any prediction of whether a failure will take minutes or days to fix.

## 4. The most real open gaps

**A. A free "why-trace" tool plus an accuracy scorecard**
- **Who has it:** students and FPGA developers on Icarus/Verilator, and anyone choosing an AI debug tool.
- **Why existing tools don't cover it:** the commercial tools need licences. wave-mcp is built for agents, its viewer runs only on Linux, and it publishes no line-level accuracy. ossschem and slang-server trace statically, one manual hop at a time.
- **What to build:**
  - Build a driver graph from the Yosys netlist, where every cell carries its source file and line.
  - Read the dump with pywellen.
  - `why(signal, t)` follows the input that was actually active, steps back across clock edges, and stops at the first divergence from a passing run.
  - Every hop links to file:line and moves the Surfer cursor over WCP. Expose it to Claude as an MCP tool.
  - Score it on 5-10 real bugs against an agent that only sees the raw dump.
- **Hackathon slice:** demoable in about 15 hours across 3 people. It fits Decap, which already runs Yosys.
- **Tracks:** G-Research (makes the hidden cause chain visible), JetBrains (a developer tool), Instalily (an agent tool), MetaView (the scorecard).

**B. "Explain my formal failure"**
- **Who has it:** SymbiYosys users, including Decap's own proofs.
- **Why existing tools don't cover it:** SymbiYosys issues [#80](https://github.com/YosysHQ/sby/issues/80) (no markers when a property starts or fails) and #83 (enums shown as 0/1) are still open. Edinburgh's own [PRAMANA](https://github.com/eelab-dev/EEdigits) explains failures but needs a hand-written case file for each one.
- **What to build:** read SymbiYosys results, then:
  - put markers in Surfer at the cycle where the property was triggered and the cycle where it failed;
  - decode enum values into their names;
  - show only the signals that affect the property;
  - write a plain-English explanation that is only allowed to cite signals and cycles present in the trace;
  - add an automatic vacuity check (does the property ever trigger?) and a few mutants to test the assertion's strength.
- **Hackathon slice:** demoable. The story is an AI-written assertion that gets flagged as vacuous, then a fixed version that catches a planted bug.
- **Tracks:** G-Research, JetBrains. Contact the PRAMANA group.

**C. Spec triangulator**
- **Who has it:** anyone working from a prose spec, and anyone using LLMs to generate RTL.
- **Why existing tools don't cover it:** [VClare](https://arxiv.org/html/2607.24854v1) never checks the testbench. [SpecLens](https://arxiv.org/abs/2609.16729) resolves ambiguity silently instead of asking. Bronco is closed.
- **What to build:** link each spec sentence to the RTL and to the test checks. Then generate 2-3 candidate implementations, simulate them, and turn the first point where they disagree into a clarifying question with two small waveforms.
- **Hackathon slice:** demoable on RTLLM's serial2parallel, the cycle-8-vs-9 ambiguity that [VeriRefine](https://arxiv.org/abs/2607.18519) could not see.
- **Tracks:** Instalily (an adaptive agent that asks), MetaView (best overall).

**D. Regression triager for cocotb/Verilator**
- **Who has it:** small teams with hardware CI.
- **Why existing tools don't cover it:** commercial tools group failures by log message, and [ReportPortal](https://reportportal.io/docs/analysis/AutoAnalysisOfLaunches/) is free but text-only.
- **What to build:** cluster failures using the assertion's scope and the first divergent signal. Rerun one seed per cluster with dumping on, open Surfer at the failure, run `git bisect`, and score the result against a regex baseline on planted bugs.
- **Hackathon slice:** demoable.
- **Tracks:** JetBrains, Instalily.

Runners-up: a free pass/fail first-difference viewer, a Tiny Tapeout "will my design fit?" pre-flight check, a register-contract checker, and a mutation-scored LLM checker generator.

## 5. Honest caveats

- **Vendor numbers are unverified.** Almost every speed-up figure is vendor-reported or comes from sponsored posts: Cadence's 89-97% and 7x, ChipAgents' 56.3%, Bronco's single case study, Silogy, IDS-AI, MODELZEN. None has an independent benchmark.
- **Some vendor capabilities are second-hand.** Cadence pages returned 403 and Siemens Visualizer returned 404 during research.
- **Watch the study years.** The 5% first-silicon figure is from 2026; "75% of projects behind schedule" is from the [2024 study](https://semiengineering.com/first-time-silicon-success-plummets/). Some evidence is old: Samsung 2021, Intel's UPF paper from 2014.
- **The adversarial checker found several gaps narrowed or closed:**
  - wave-mcp already does waveform search, transaction latency, driver/X tracing and pass/fail diff for free, so Gap A must clearly differentiate from it.
  - [Tsunami](https://pypi.org/project/tsunami-wave/) is already a waveform query engine.
  - GTKWave and Vaporview already expand a bus into its bits.
  - [MCY](https://github.com/YosysHQ/mcy) already grades checkers by mutation testing, for free.
  - [EBMC](https://github.com/diffblue/hw-cbmc/tree/main/regression/verilog/SVA) already supports full concurrent SVA for free.
  - [SpiceBind](https://pypi.org/project/spicebind/) already runs SPICE inside cocotb tests, and [CPAS](https://dvcon-proceedings.org/wp-content/uploads/118-CPAS-Cocotb-Power-Aware-Simulation-Framework.pdf) shows open power-aware simulation (as a paper).
  - Also already available: VClare's ambiguity benchmarks, slang-server's automatic setup, cocotb IDE debugging via debugpy, and Verilator's new covergroup and UVM 2020 support.
  - DSim Cloud has shut down.
- **Recent work may be missing.** Both research passes ran out of web search early, so findings come from fetching known pages directly. Papers and startups from 2025-26 may not be covered.
